# 项目介绍 — 旅游信息管理平台(面试用)

> 用途:面试自我介绍后的项目讲解 + 追问预案。建议讲 2~3 分钟,亮点部分等面试官追问再展开。

---

## 一、30 秒开场白(可直接背)

> 我最近独立完成了一个**旅游信息管理平台**的前后端分离项目,我负责整个前端。系统分**用户端**和**管理端**两个端:用户端提供景点、攻略、路线的浏览,收藏、评论、门票下单,以及一个**智能路线规划**功能;管理端提供内容管理、审核、订单管理、数据可视化大屏等能力。技术上用的是 **Vue 3 + Vite + Element Plus + Pinia**,地图和驾车规划接入的是**高德地图 JSAPI**,整个项目从 0 到 1 大概一个月完成。

## 四、技术亮点(重点准备,等追问再展开讲)

### 亮点 1:纯前端实现的智能路线规划 ⭐(最值得讲)

**场景**:用户选定若干想去的景点,系统自动算出"最顺路"的游览顺序,并在地图上画出驾车路线。

**方案**:
- 相邻景点间的直线距离用 **Haversine 公式**(球面距离)计算,构建距离矩阵;
- 求访问顺序本质是一个 **TSP(旅行商)问题**,考虑到景点规模通常只有个位数到十几个,采用 **最近邻贪心算法**:从起点出发,每步选距离当前景点最近的未访问景点,O(n²) 复杂度完全够用;
- 得到顺序后调用**高德 AMap.Driving 驾车规划插件**逐段绘制真实驾车路线与耗时,并复用插件实例避免重复加载;
- 全程**不新增后端 API**,是一个纯前端算法模块,方便独立测试。

**可以延伸的点**(面试官大概率追问):贪心是近似解不是全局最优;数据量更大可以换 2-opt 局部优化或分支限界;直线距离和真实路网有偏差,所以最终以高德驾车结果为准,贪心只负责排顺序。

### 亮点 2:双端单应用的路由与权限设计

- 一套 SPA 同时承载用户端与管理端,通过路由 `meta`(`requiresAuth` / `requiresAdmin`)+ 全局导航守卫控制;
- 两端布局各自独立(`UserLayout` / `MainLayout`),用户端整体挂在 `/travel/home` 前缀下,**主动避开了与管理端 `/travel` 子路由的路径冲突**(这是我踩过坑后刻意设计的);
- 登录/注册页设 `noAuth`,已登录访问会按角色自动重定向到对应首页。

### 亮点 3:Axios 统一封装与静默降级

- 响应拦截器统一处理后端 `{code, msg, content}` 结构,错误统一 ElMessage 提示;
- 识别"没有找到数据"的空结果,放行给页面渲染空列表而不是弹错误——**空态是正常业务,不是异常**;
- 请求可传 `silent` 标记,接口未就绪时静默降级,页面自己渲染空态/占位,保证部分接口缺失时整个页面仍可用;
- 401 时清理 Pinia store 与 localStorage 双份登录态,带 `redirect` 参数跳回登录页,登录后回跳原页面。

### 亮点 4:高德地图的安全接入与优雅降级

- Key 与安全密钥通过 `.env.local` 环境变量注入,**不进仓库**;
- 运行时检测 Key 是否已配置,未配置时地图模块整体降级(展示占位),不影响其他功能;
- 驾车插件动态注册、实例复用,减少重复开销。

### 亮点 5:性能与体验细节

- **35 个路由全部懒加载**(`() => import`),按需分包;
- Element Plus **图标不全局注册**(全量注册 300+ 组件会拖慢启动),组件内显式按需引入;
- 列表页首屏用**骨架屏**,翻页用 `v-loading`,空数据用统一的空态插画组件;
- 一段真实的踩坑:登录后返回的用户对象**带着密码哈希字段**存进了 localStorage,后续编辑资料时整包回传,后端对密码字段二次加密,导致用户"没改密码却登录不了"。解决方案是落库前**解构剔除 password 字段**,从源头隔离敏感字段。

## 五、高频追问预案(Q&A)

**Q1:为什么路线规划用贪心,不用动态规划/遗传算法?**
> 景点规模小(通常 <20 个),贪心 O(n²) 的结果与最优解差距可接受,实现简单、无依赖;而且贪心输出会立刻被高德真实驾车距离"校准"。若规模变大,规划用 2-opt 或 DP(Held-Karp, n<20 时也可行)都是局部替换,代码结构上预留了切换空间。

**Q2:为什么路线规划放前端做,不让后端算?**
> 这是展示层的交互逻辑(顺序、地图绘制),不涉及持久化和多端共享;纯前端实现零接口依赖、响应快、好测试。如果未来要跨端(小程序)共享规划结果,再下沉到后端也不迟。

**Q3:Token 存 localStorage 不怕 XSS 吗?**
> 知道这个 trade-off。当前项目后端未配 CORS 域名白名单和 Refresh Token 机制,localStorage 是最直接的方案;更稳妥的做法是 HttpOnly Cookie + CSRF Token,或短期 Access Token + Refresh Token 双令牌。这是我明确知道、暂时接受的技术债。

**Q4:两个端为什么放一个项目里?拆开不更好吗?**
> 管理端页面量不大,拆开反而多一套构建/部署/依赖维护成本;共用登录、请求封装、工具函数收益明显。用独立的 Layout + 路由前缀做了物理隔离。若管理端继续膨胀,可平滑拆成两个入口(多页应用模式)。

**Q5:`silent` 降级是怎么设计的?**
> 在 axios 配置上加一个自定义字段,拦截器里判断:非 silent 的业务失败才弹全局提示。用于"后端接口可能还没实现"的联调期和部分模块异常时不阻塞整页。代价是错误提示的分寸要靠约定,所以只在明确需要降级的页面使用。

**Q6:项目里你觉得最有挑战的事?**
> 建议讲上面"密码哈希整包回传"那个 bug:现象诡异(用户没改密码却登录不上)→ 排查链路(localStorage → 编辑资料整包提交 → 后端二次加密)→ 修复(落库前剔除敏感字段)→ 复盘(返回给前端的对象要做字段白名单,而不是全盘接收)。这是一个完整的"现象-定位-修复-沉淀"故事。
