# 门票库存与订单取消实施规划

> 状态：后端已实现并编译通过，集成测试待隔离库执行；版本：v1.3；最后更新：2026-11-10。本文是门票库存开发的执行基准。目标仓库：`D:\IDEA\IdeaProjects\travel-0`。**代码完成不等于验收完成：并发与回滚测试仍需在专用测试库运行，前端尚未适配新接口。**

## 1. 已核对的现状与结论

- `ScenicOrdersController.add` 当前按请求体 `userId.id` 做 5 秒防重，随后调用 `ScenicOrdersServiceImpl.insert` 插入，再发消息；未校验余票。订单号是毫秒时间戳 + 三位随机数，存在并发碰撞概率。
- `ScenicOrdersEntity` 有 `playDate`（String）、`ticketCount`、`totalAmount`（Double）、`payStatus`；没有库存与订单业务状态。`ScenicEntity.price` 为 Double。订单 Mapper 使用手写 XML，`insert` 已启用 `useGeneratedKeys`，但 `update` 能改订单关键字段，`deleteById` 是软删除。
- 当前 `GlobalExceptionHandler` 仅处理鉴权 401/403；业务失败应仍返回 HTTP 200 + `ReturnVO.code=0`，异常必须先让事务回滚，再在事务外转换为业务响应。
- 项目已有 `SecurityUtil.currentUserId()`、真实 Redis 的 `@SpringBootTest` 测试风格；未发现现有 `@Transactional`。最终上线前仍需对真实 MySQL 的实际表结构、索引、字段类型、存量数据和历史订单状态执行基线核对，不能只凭实体和旧文档做迁移。
- **方案总体正确、可在现有 Spring Boot + MySQL 技术栈实现，工作量中等**；真正的难点是存量数据迁移、所有修改/删除入口闭环、事务边界与并发验收，不是库存扣减 SQL 本身。

## 2. 范围与核心约束

本期做：库存表与迁移、未来 30 天库存定时生成、原子扣减、事务下单、手动及 30 分钟超时取消回补、模拟支付、订单状态与安全收口、并发及回滚测试、接口和项目文档更新。可选：余票查询接口。暂不做 Redis 预扣、Seata、分段库存、真实支付/退款网关、学生/团体票。`ticket_type_id=1` 表示当前唯一成人票，未来多票种才扩展；不因此虚构票种业务。

**MySQL 是库存唯一真相。** Redis 的 5 秒防重仅控制短时重复提交，Redis 故障会降级放行，不能替代数据库扣减，也不等于持久的请求幂等。所有库存相关表采用 InnoDB，订单及两张库存表在同一个数据源/同一个本地事务中操作。不得在事务内发送消息或访问外部服务。

## 3. 数据模型与迁移

### 3.1 新表

| 表 | 字段和索引 | 规则 |
|---|---|---|
| `scenic_stock` | `scenic_id`, `play_date` DATE, `ticket_type_id` INT DEFAULT 1, `total` INT, `remaining` INT, `version` INT DEFAULT 0；唯一键 (`scenic_id`,`play_date`,`ticket_type_id`) | 票种可售库存；`0 <= remaining <= total`，数量非负；单票种本期仅 type=1 |
| `scenic_capacity` | `scenic_id`, `play_date` DATE, `total` INT, `remaining` INT；唯一键 (`scenic_id`,`play_date`) | 景区当日承载总量；本期可与成人票库存总量一致，但分别维护 |

可按现有数据库风格增加自增主键、创建/更新时间和外键/索引；即使有主键，组合唯一键也必须保留。建表字段使用非空与默认值约束；如当前 MySQL 版本支持并实际执行 CHECK，再增加非负/不超过 total 的约束，不把 CHECK 当成唯一防线。**两表的 `remaining` 可能不相同，展示可售数量应为两者的较小值；缺任一记录即不可售。** 后续有多票种时，容量总量与所有票种之和的关系必须另定，不能简单假设两者永远相等。

### 3.2 库存生成与管理配置

- 系统可配置的全站默认容量和成人票库存初始值均为 **100**；景区可配置长期默认容量/成人票库存覆盖值，定时任务为该景区生成新日期时优先取景区覆盖值，否则取全站默认值。当前仅一种票，容量和票种默认均为 100；后续调整为独立配置时仍以两者较小值为可售上限。
- 以 `Asia/Shanghai` 的自然日为准，维护**含当天的 30 个日期**：当天为第 1 天、当天 +29 天为第 30 天。定时任务每日运行并补齐范围内**缺失**的景区日期记录；已有记录不可覆盖 `total/remaining`，应通过组合唯一键和安全的幂等插入防止任务重跑重置已售库存。系统首次部署先补齐这一窗口。景区下架后停止为其生成新日期，已有订单及库存不因下架而自动清除。
- 管理员可配置景区长期默认值，另可单独调整某景区某日期的容量及成人票库存；修改时保持已占用票数不变：`sold_or_reserved = total - remaining`，新 `total >= sold_or_reserved`，新 `remaining = new_total - sold_or_reserved`；更新需在事务内进行、先容量后票种，避免并发修改造成超卖。管理员不可直接把当日剩余量重置为默认值。
- `scenic` 增加后台可编辑的**当日票停止时间**，默认 `17:00`（按 `Asia/Shanghai`）。仅允许下单日期在 `[今天, 今天+29天]`；过去日期、超过窗口的日期一律拒绝；若游玩日期为今天，**到达 17:00 当刻即停止下单**，未来日期不受当天截止时间限制。景区修改截止时间只影响之后创建的订单，已创建订单不追溯取消；后端校验，不依赖前端时钟。

### 3.3 订单表变更

`scenic_orders` 新增 `status`（0 待支付、1 已支付、2 已取消、3 已完成）、`cancel_time`、`unit_price`（DECIMAL(10,2)）以及 **`ticket_type_id`（默认 1）**。虽然需求写“只在表结构上预留 ticket_type_id”，但订单必须保存票种快照，否则未来取消时无法确定回补哪条票种库存。`order_no` 添加唯一索引前，先查历史重复值、空值和索引现状；新订单号改用低碰撞算法（例如 UUID/雪花 ID）并适配现有列长度，唯一约束冲突仍应让本次事务回滚并返回可重试失败。

存量 `pay_status=1` 回填 `status=1` 并保留；存量 `pay_status=0` 直接改为 `status=2`（已取消）、记录迁移取消时间，**不逻辑删除、不回补库存**，使用户仍可查看历史订单。旧文档曾提及 `pay_status=2`，迁移前必须检查真实取值及空值，逐类确认映射，不能盲目套用未支付规则。增加订单级 `stock_reserved` 标记（历史=0，新下单=1）；手动/自动取消仅对实际预留过库存的订单回补。迁移脚本要有预检查、分阶段执行、回滚/备份方案和数据校验 SQL；上线时先生成未来日期的容量与票种库存，再开放新下单。

> 表数口径：原项目介绍写 **10 张**；本方案新增 `scenic_stock` 和 `scenic_capacity` **两张**，完成后应写 **12 张**，不是 11 张；订单增加字段不算新表。文档数目只在实际落库后修改。

## 4. API 与状态机

| 接口 | 规划行为 |
|---|---|
| `POST /scenicOrders/add` | 必填有效 `scenicId.id`、`playDate`（严格 `yyyy-MM-dd` 且符合可售日期策略）、`ticketCount > 0`；联系人按现有规则校验。当前只支持成人票；金额在后端按景区当前价格计算，金额使用 BigDecimal/DECIMAL 两位小数，不信任请求 `totalAmount`、`unitPrice`、`payStatus`、`status`、`userId`、`orderNo`。用户来自 token，`payStatus=0,status=0`。继续保留 `ReturnVO`，成功在 `content` 中返回 `{id,orderNo}`，现有 `code/msg` 语义不变。 |
| `POST /scenicOrders/cancel/{id}` | 本人或管理员；仅 `status=0` 可取消，其他状态拒绝；执行条件状态更新和库存回补的单一事务。不逻辑删除；已取消再次调用返回业务失败，不重复回补。 |
| `POST /scenicOrders/pay/{id}`（模拟支付） | 仅订单本人、且订单仍为 `status=0` 且创建后未满 30 分钟可提交；服务端以条件状态更新原子改为 `status=1,pay_status=1`，记录支付时间；不调用支付网关、不再扣库存。与超时取消并发时仅一方能成功。 |
| `GET /scenic/stock?scenicId=&playDate=` | 可选；展示 `min(capacity.remaining, stock.remaining)`，无记录按“暂未开放”，有记录余量为 0 按“已售罄”；只作展示，最终下单结果以数据库原子更新为准。 |
| `POST /scenicOrders/edit` | 改用独立白名单 DTO + 专用 SQL，且校验订单状态，只允许必要的非库存字段（如联系人）；禁止改 `userId/scenicId/playDate/ticketCount/ticketTypeId/orderNo/totalAmount/unitPrice/payStatus/status/payTime`，不能只在 Controller 忽略字段而保留可直达的通用 Mapper 更新。 |
| `POST /scenicOrders/deleteById/{id}` | 待支付订单直接软删除必须拒绝，不能绕开取消回补；自动超时及迁移取消订单均保留为可查询历史，不能自动逻辑删除。其他状态的删除权限与历史保留策略应遵循既有规则，不得构造库存回补捷径。 |

`pay_status` 和 `status` 保留兼容字段，明确由服务端维护的一致性：新单二者为 0，模拟支付成功二者为 1，取消则 `status=2`、`pay_status` 保留未支付语义 0；历史已支付为 1。本期删除“管理员手工标记支付”业务，禁止客户端通过 edit 标记付款或退款；只允许订单本人通过模拟支付入口完成 `0→1`，取消只允许 `0→2`，完成 `1→3` 本期不开放操作入口。已支付订单退款不属于本期范围。订单列表、详情、前端按钮与旧文档中“编辑支付/退款”的约定须同步修改。

## 5. 下单、取消事务

### 5.1 下单

在 Controller 完成参数检查、获取 `SecurityUtil.currentUserId()` 和 5 秒防重后，调用**另一 Spring Bean 的 public `@Transactional(rollbackFor = Exception.class)`** `createOrder`；不能用同类内部调用绕开 Spring 事务代理。服务层再次以可信用户 ID/请求 DTO 为输入，读取景区当前有效价格、状态与当天截止时间，并基于服务端 `Asia/Shanghai` 时钟校验 `[今天, 今天+29天]` 和当天 17:00（或景区覆盖时间）截止，以 BigDecimal 算 `unitPrice × ticketCount`，构造订单票价快照。

事务内按统一顺序：

1. `UPDATE scenic_capacity SET remaining=remaining-:n WHERE scenic_id=:id AND play_date=:date AND remaining>=:n`；
2. `UPDATE scenic_stock SET remaining=remaining-:n, version=version+1 WHERE scenic_id=:id AND play_date=:date AND ticket_type_id=1 AND remaining>=:n`；
3. `INSERT scenic_orders ...` 并获得自增 id。

每步更新行数必须恰好为 1，插入也须成功；任何失败抛运行时业务异常或显式指定回滚的异常，**不在事务内 catch 后直接返回 `false/ReturnVO`**。若需区分“暂未开放”和“售罄”，可在更新失败后以只读查询做错误归因（不以查询结果作扣减前提），或在事务外诊断；诊断受并发影响，提示只能尽力准确，不能破坏原子性。事务完成后才由 Controller（或提交后事件）发站内消息；消息失败只记录日志，不回滚已提交订单。若业务失败，事务外转换 `ReturnVO(code=0,msg=...)`。

### 5.2 手动与超时取消

在事务内读取待取消订单快照（含用户、景区、游玩日期、票种、张数及是否曾预留库存），手动取消做本人/管理员校验；随后先 `UPDATE scenic_orders SET status=2,cancel_time=NOW() WHERE id=:id AND status=0 AND del_mark=1`，更新数非 1 则拒绝。**只有状态成功变化、且订单确实预留过库存才回补**；按照项目统一资源顺序先回补 `scenic_capacity`、再回补 `scenic_stock`，两者 `UPDATE remaining=remaining+:n WHERE ... AND remaining+:n<=total` 均须影响 1 行，否则抛异常使状态更新回滚。不能先回补再改状态；不能让编辑/软删除成为另一条隐蔽取消路径。取消后的站内通知同样放在提交后。取消订单保留在历史列表，**不逻辑删除**；用户可以看到“已超时取消”（建议增加取消原因字段区分自动超时/手动/历史迁移）。

**本期必须提供自动超时任务**：以订单创建时间 +30 分钟为截止，批量扫描仍为待支付且已到期的新订单，分页/分批调用独立事务 Bean 的取消方法；每单先条件改状态（同时约束 `create_time <= 当前时间-30分钟`），再回补，不在一个大事务里处理全部订单。任务可重复执行，重复扫描或多实例同时执行只能有一方更新成功，其余不回补；失败单记录日志并下轮重试，任务扫软删以外的待支付订单，不删除已取消历史。用数据库当前时间作到期判定，尽可能减少应用/数据库时钟偏差。

### 5.3 模拟支付

仅订单本人可调用模拟支付；数据库条件更新必须同时要求 `status=0`、`del_mark=1`、创建时间**未满 30 分钟**，成功时一次性设置 `status=1,pay_status=1,pay_time=NOW()`，影响行数为 1 才算成功；不进行额外库存变化。满 30 分钟即使超时任务尚未扫描也不可支付。支付和自动/手动取消并发争同一订单条件状态更新，最多一个成功；模拟支付成功后不再允许取消回补。模拟支付成功消息在事务提交后发送，失败不可发“支付成功”通知。

所有写库存的业务路径统一“容量→票种”顺序；状态行锁与这两行库存锁同时持有时须评估死锁，在集成测试中涵盖并发下单/取消。MySQL 死锁或锁等待超时应回滚并给出可重试响应（需要时做有限次数整事务重试，不在部分 SQL 上盲目重试）。`version` 本期仅作为预留/变更计数，不与条件扣减混用为第二套并发控制。

## 6. 实施顺序与交付检查

1. **基线**：确认目标库 `SHOW CREATE TABLE scenic_orders/scenic`、历史 `pay_status` 分布、重复 `order_no`、景区价格类型、删除调用方；检查迁移时旧支付状态特殊值。库存默认 100、按景区覆盖、历史未支付取消不回补已确定。先确定金额精度：若 `scenic.price` 或 `scenic_orders.total_amount` 是浮点类型，应规划改为 DECIMAL 并核对历史精度。
2. **迁移**：编写可审查的 SQL 脚本（含新表、订单新列/唯一索引、历史数据映射和验证 SQL）；测试库执行并记录结果，不自动覆盖生产数据。
3. **代码**：实体与 DTO、Mapper/XML 原子更新、事务 Service、add/cancel/pay、30 天库存生成与管理员覆盖、30 分钟超时任务、当日截止时间、编辑/软删除收口、可选余票接口；统一业务异常返回。
4. **测试**：沿用 `@SpringBootTest` + 真实 MySQL/Redis；独立测试账户、景区与唯一未来日期，`@BeforeEach` 建数据，`@AfterEach` 清订单/库存/Redis 防重 key。并发测试不能把 20 个服务调用包在同一个测试事务中；用 `CountDownLatch` 同时起跑、每线程独立事务、等待所有 Future 并断言结果。**20 并发抢 10 张时绕过或使用不同用户/不同防重 key**，否则 5 秒防重会先挡掉 19 个，无法验证库存并发。
5. **验收**：10 成功/10 失败、容量及票种余量都为 0 且无负数；0 库存失败（`code=0`、售罄、无新增订单）；缺库存显示暂未开放；同用户 5 秒重复提交只有 1 张；两次取消仅回补一次；人工注入订单 INSERT 失败则两种库存均回滚；取消时回补失败则订单状态回滚；跨用户取消 403；每天补齐含当天的 30 天、重跑不重置库存；按景区覆盖与改单日总量不超卖；今天截止前/后、过去/第 31 天边界；支付在 30 分钟内成功、到期拒绝、支付与取消竞争只能一方成功；自动取消保留历史并仅回补一次；旧列表/详情/鉴权/订单消息回归通过。
6. **文档**：完成并验收后更新根 `README.md`、`docs/项目介绍.md`（10→12 张）、`docs/简历项目经验.md`、`docs/scenicOrders接口说明.md`、`docs/前端接口对接说明.md`；项目经验仅写已实际验证成果，不把规划冒充实现。文档索引维护状态。

## 7. 已确认的业务决定与实施前技术核查

- 库存由系统定时任务维护含当天的未来 30 个自然日；系统默认成人票与场地容量均为 100，管理员可配置景区长期覆盖值与单日调整；已有记录不覆盖。当日停止时间景区可改、默认 17:00，按 `Asia/Shanghai`；已生成订单的 `unit_price` 快照不随景区票价变更。
- 存量未支付订单迁移为已取消且保留可见，不逻辑删除、不回补；新订单超时 30 分钟自动取消并回补，同样保留历史且显示“已超时取消”。
- 仅订单本人可在 30 分钟内模拟支付；不支持管理员手工标记支付、前端 edit 支付/退款；模拟支付不调用真实网关。
- 以上规则无待确认业务问题。已只读核验本地 MySQL 8.0.45：`order_no` 原已有唯一索引，`scenic.price`/订单总额为 DECIMAL(10,2)；迁移前旧订单 0/1/2 分别 4/26/7 条，其中一条旧未支付原已软删。用户运行迁移后核验：两张库存表及六个订单新列存在，旧已支付 26 条仍为已支付，未支付 4 条标为 `LEGACY_UNPAID`、旧退款 7 条标为 `LEGACY_REFUNDED`，历史单预留标记均 0，新库存表尚为空。未对迁移做重复执行。
