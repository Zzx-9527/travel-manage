## 三、架构设计亮点

### 1. 统一响应模型

所有接口统一返回 `ReturnVO` 对象：

```json
{
  "code": 1,        // 1 成功，0 失败
  "msg": "操作成功",
  "content": {}     // 实际数据
}
```

前端可以基于 code 做全局拦截（如 401 跳转登录页），无需每个接口单独处理异常状态。代码风格统一，维护成本低。

### 2. Sa-Token 会话鉴权

- 登录成功后调用 `StpUtil.login(userId)`，生成随机 token（`tik` 风格，**不是 JWT**），会话写入 Redis（key 前缀跟随 `token-name`，当前为 `Authorization:login:*`）
- 客户端通过 `Authorization: Bearer <token>` 携带；`SaInterceptor` 统一校验，登录、注册、接口文档走白名单
- 鉴权异常由 `GlobalExceptionHandler` 统一转成 HTTP 401 / 403 + `ReturnVO`，前端按状态码处理
- 后台能力：`/travelUser/online` 查看在线用户（SCAN 聚合多端 token 数），`/travelUser/kickout/{id}` 强制下线；`StpInterface` 把 `userRole` 映射为 `admin`/`user`，后台接口用 `@SaCheckRole("admin")` 控制
- **收益**：登出立即失效、可踢人下线、30 分钟无操作自动过期，解决了 JWT 签发后无法作废的问题；代价是每次鉴权多一次 Redis 查询（本地亚毫秒级）

### 3. 消息通知组件的解耦设计

封装了 `MessageNotifier` 组件，内部注入 `MessageService`：

```java
// 业务层只需一行代码
messageNotifier.sendOrder(userId, "下单成功", "xxx门票生成订单 " + orderNo);
```

关键设计点：
- 消息发送全部用 `try-catch` 包裹，**异常只记日志，绝不抛到上层**
- 消息发送失败不影响订单生成、审核状态变更等主业务流程
- 实现了「消息通知」与「核心业务」的逻辑解耦，后续如果换成 MQ 或增加短信渠道，只需修改 `MessageNotifier` 内部实现

### 4. Combo 模式：分层架构

严格遵循 **Controller → Service → Mapper** 三层架构：

- **Controller**：只做参数接收、响应返回，不含业务逻辑
- **Service**：封装业务逻辑，事务管理
- **Mapper**：数据访问层，使用 MyBatis-Plus BaseMapper

每层职责单一，便于单元测试和维护。

### 5. MyBatis-Plus 实体关联的对象映射

对于多对一关联（如订单 → 用户、路线详情 → 景点），实体层直接使用对象引用：

```java
// 订单实体中直接引用用户和景点对象
public class ScenicOrdersEntity {
    private TravelUserEntity userId;  // 关联用户
    private ScenicEntity scenicId;     // 关联景点
}
```

Mapper XML 中通过 `<association>` 标签配置关联查询，MyBatis-Plus 自动完成结果映射。避免了在业务代码中手动编写大量 Join 查询和 ResultSet 转换。

### 6. MyBatis-Plus 自动填充

通过 `MyMetaObjectHandler` 统一处理公共字段：

| 字段 | 填充时机 | 说明 |
|------|---------|------|
| `createTime` | INSERT | 插入时自动填入当前时间 |
| `updateTime` / `payTime` | INSERT + UPDATE | 插入和更新时自动更新 |

所有实体只需声明 `@TableField(fill = FieldFill.INSERT)` 注解，无需在每个 Mapper 或 Service 中重复设置时间。

### 7. 文件上传与防重名

- 配置了 multipart 上传限制（最大 10MB）
- 使用 `时间戳 + 序号` 生成唯一文件名，**彻底避免重名覆盖**
- 支持图片 / 视频等多种 MIME 类型

### 8. 统一 CORS 跨域配置

通过 `CORSConfiguration` 配置全局跨域过滤器，允许所有来源和请求方法，前端开发时无需在浏览器端解决跨域问题。

### 9. 门票库存与订单事务（新增）

- **库存模型**：`scenic_capacity`（景区日承载）与 `scenic_stock`（票种日库存，本期仅成人票 `ticket_type_id=1`）分别记录 `total/remaining`，唯一键集中在“景区 + 日期（+ 票种）”；可售余量取两者较小值，缺任一记录视为未开放。
- **不超卖**：下单在同一个本地事务里先扣容量、再扣票种、最后写订单，扣减统一使用 `UPDATE ... SET remaining = remaining - n WHERE ... AND remaining >= n`，以影响行数判定成败，不做“先查后改”，也不依赖 Redis 或分布式锁；票种扣减同时 `version = version + 1`。
- **取消回补**：先 `UPDATE ... SET status=2 ... WHERE id=? AND status=0`，只有状态确实变更成功的请求才回补库存，重复取消返回失败，避免重复回补；回补同样带 `remaining + n <= total` 条件。
- **超时取消与模拟支付**：未支付订单满 30 分钟由定时任务按 `create_time` 分批扫描并逐单取消；模拟支付与取消都通过带状态条件的单条更新抢占订单，二者并发最多成功一个。定时任务按 id 游标翻页，失败单下一轮重试，多实例重复执行也不会重复回补。
- **库存生成**：每日任务为在售景区补齐“今天 ~ 今天+29 天”的缺失记录，使用 `INSERT IGNORE` + 组合唯一键保证幂等，已存在记录不重置已售库存；景区可配置长期默认值与当日停售时间（默认 17:00）。
- **价格与身份**：下单人取自 token，金额由服务端按景区当前价格计算并以 `unit_price`/`total_amount` 做快照；历史订单没有可靠单价快照时保持 `null`，不用当前票价伪造历史。
- **历史数据**：迁移把旧未支付订单标记为已取消（`LEGACY_UNPAID`）、旧退款标记为 `LEGACY_REFUNDED`，`stock_reserved=0`，因此历史订单不会触发新库存回补。

## 五、项目难点与解决方案

| 难点 | 解决思路 |
|------|---------|
| **实体关联复杂**：订单关联用户和景点，路线详情关联路线和景点，多层嵌套 | 实体中使用对象引用，Mapper XML 通过 `<association>` 配置自动映射，MyBatis-Plus 自动完成结果组装，避免手写大量 Join 和 ResultSet 转换 |
| **消息通知不能影响核心业务**：下单成功要发通知，但如果消息服务异常不能导致下单失败 | 消息发送全部 try-catch 包裹，异常只记日志不抛错，保证核心业务流程不受影响。后续可替换为 MQ 实现异步削峰 |
| **JWT 校验失败的处理**：Token 过期或被篡改时不能报 500 或空指针 | 改用 Sa-Token 统一鉴权，`GlobalExceptionHandler` 把未登录/角色不足翻译成 401/403 + `ReturnVO`，业务异常仍返回 HTTP 200 + `code=0` |
| **文件上传重名覆盖**：高并发场景下多个用户同时上传可能文件名冲突 | 使用`时间戳(毫秒) + 自增序号` 生成唯一文件名，理论上同一毫秒可生成 99 个不重复文件名，彻底避免冲突 |
| **路线行程按天组织**：每条路线包含多天行程，每天包含多个景点，需要有序展示 | 设计 `route_detail` 表，通过 `day_no`（第几天）+ `sort`（当日排序）两个字段共同控制顺序，查询时 `ORDER BY day_no, sort` |

1. **一句话定位**："后端是一个基于 Spring Boot 2.7.5 + MyBatis-Plus + MySQL 的 RESTful 服务，提供了 40+ 个接口支撑前端业务。"

2. **技术选型**："框架用了 Spring Boot，ORM 用的 MyBatis-Plus 减少样板代码，鉴权用 Sa-Token 把会话存 Redis（支持登出、踢人、超时续期），缓存用 Redis 做景点详情的 Cache-Aside，密码用 BCrypt 加密，接口文档用 Knife4j + SpringDoc。"

3. **架构亮点**："我在设计上做了几个关键决策——统一 ReturnVO 响应模型让前后端联调很顺畅；用 Sa-Token 替换 JWT 解决了 token 无法主动失效的问题；缓存层封装了 Cache-Aside 模板，内建空值缓存、TTL 抖动、手写互斥锁和异常降级；消息通知组件做了 try-catch 兜底，保证消息异常不影响核心业务。"

4. **个人贡献**："这个项目的后端是我从零搭建的，完成了从数据库建模到全部接口开发，包括鉴权、消息通知、文件上传等通用能力的封装。"
