# 景点详情接口压测报告

> 日期：2026-10-31 ｜ 版本：v1.0 ｜ 对应阶段：Phase 6
> 结论先行：**缓存把数据库查询从"每请求 1 次"降到 0，吞吐提升 12.5%–16.6%，P95 下降 15.6%–20.7%**；在本机小数据量场景下，收益被鉴权与 Web 层开销稀释，详见 §5。

---

## 1. 测试环境

| 项 | 值 |
|---|---|
| 机器 | Windows 本机（客户端与服务端同机，回环网络） |
| JDK | 1.8.0_201 |
| 应用 | Spring Boot 2.7.5，内嵌 Tomcat，可执行 jar |
| 数据库 | MySQL 8.0.45，`travel_management`，HikariCP（max=20） |
| 缓存 | Redis 8.10.3，Lettuce + 自定义 `RedisTemplate` |
| 数据量 | `scenic` 12 行、`scenic_orders` 39 行（数据量很小，见 §5 局限） |
| 应用参数 | `--server.port=18081`，关闭 MyBatis 的 stdout SQL 日志 |

---

## 2. 测试对象

**GET** `/travel/scenic/queryById/1`（景点详情，Cache-Aside）

- 热缓存：命中 `travel:v1:scenic:detail:1`，不查库；
- 无缓存：`--travel.cache.enabled=false`，每次请求直接查库（`scenic` 与 `scenic_category` 的 JOIN）。

对比时**只切换缓存开关**，其余配置、数据、并发参数完全一致。

---

## 3. 测试方法

- 压测工具：[`tools/LoadTest.java`](../tools/LoadTest.java)（JDK 8 单文件，`HttpURLConnection` + 固定线程池）。
  没有用 PowerShell 的 `Invoke-WebRequest`，因为它单次调用自带十几毫秒客户端开销，会把毫秒级差异淹没。
- 每个场景先预热 100 次请求（建连 + JIT），再统计；
- 每个线程按顺序发请求，记录每次耗时，最后统一计算 P50/P95/P99；
- 并发档位：50 / 100 / 200 线程，每线程 200 次（合计 1 万 / 2 万 / 4 万请求）；
- 客户端与服务端同机，注意本机回环延迟偏低。

复现命令：

```bash
# 1) 编译压测器
javac -encoding UTF-8 -d target/loadtest tools/LoadTest.java

# 2) 启动应用（热缓存）
java -jar target/spbYq-0.0.1-SNAPSHOT.jar --server.port=18081 \
  --mybatis.configuration.log-impl=org.apache.ibatis.logging.nologging.NoLoggingImpl

# 3) 登录拿 token 后执行
java -cp target/loadtest LoadTest http://127.0.0.1:18081/travel/scenic/queryById/1 <token> 50 200 100

# 4) 无缓存对照：启动时追加
--travel.cache.enabled=false
```

## 4. 结果

### 4.1 三档并发对比

| 并发 | 场景 | QPS | 平均(ms) | P50(ms) | P95(ms) | P99(ms) | 最大(ms) | 错误 |
|---|---|---|---|---|---|---|---|---|
| 50 | 热缓存 | **6138.7** | 8.06 | 6.76 | **17.40** | **25.15** | 35.77 | 0 |
| 50 | 无缓存 | 5417.1 | 9.15 | 7.54 | 18.64 | 32.89 | 62.74 | 0 |
| 100 | 热缓存 | **11173.2** | 8.87 | 8.31 | **13.15** | **14.94** | 26.74 | 0 |
| 100 | 无缓存 | 9930.5 | 9.97 | 9.15 | 15.59 | 20.09 | 51.70 | 0 |
| 200 | 热缓存 | **9233.6** | 21.40 | 17.96 | **33.51** | **65.00** | 554.50 | 0 |
| 200 | 无缓存 | 7916.1 | 25.01 | 19.90 | 42.25 | 98.54 | 609.03 | 0 |

### 4.2 相对提升

| 并发 | QPS 提升 | P95 下降 | P99 下降 |
|---|---|---|---|
| 50 | +13.3% | -6.7% | -23.5% |
| 100 | **+12.5%** | **-15.6%** | **-25.6%** |
| 200 | **+16.6%** | **-20.7%** | **-34.0%** |

### 4.3 缓存命中与数据库压力

- 热缓存场景 10,000 次请求期间：`keyspace_hits` 增量 **40,400**、`keyspace_misses` 增量 **0**，即缓存键 100% 命中；
- 每次请求约 4 次 Redis 往返：Sa-Token 校验（token / session / last-active）+ 缓存读取；
- 数据库查询量：热缓存 **0 次**，无缓存 **10,000 次**（设计上每请求 1 次 JOIN 查询）。

---

## 5. 结果分析

1. **为什么 QPS 只提升 13% 左右**：单条主键 + 小表 JOIN 在 MySQL 里只要亚毫秒级，而每个请求还要做 4 次 Redis 往返（鉴权）和 JSON 序列化、Tomcat 调度。缓存省掉的 DB 成本占比不高，所以总延迟改善有限。
2. **为什么 P99 改善比 P95 明显**：无缓存时请求要抢 Hikari 连接（max=20），高并发下排队导致长尾拉长；缓存把这部分排队完全去掉，所以尾部收益最大。
3. **200 并发时 QPS 反而低于 100 并发**：应用侧已接近 Tomcat 线程与 Redis 单连接的处理上限，继续加压只会拉高延迟，数据符合预期。
4. **缓存的真实价值**：不在于把 8ms 变成 7ms，而在于**把数据库从读路径上摘掉**——流量增长时，DB 不再随 QPS 线性承压，这是扩容时最贵的资源。

---

## 6. 局限

- 数据量极小（12 行景点），SQL 几乎必然命中 InnoDB 缓冲池，真实环境中数据量、索引命中率、JOIN 复杂度都会让无缓存路径更慢；
- 客户端与服务端同机，回环 RTT 远低于生产网络；
- 未做长时间稳定性测试（如 30 分钟持续压测、内存/连接泄漏观察）；
- 未对比"缓存穿透保护"（空值缓存）与"互斥重建"在高并发冷启动下的效果。

---

## 7. 简历可用表述（保守、可复核）

> 对景点详情接口做缓存前后压测（本机、1 万–4 万请求、50/100/200 并发）：**数据库查询从每请求 1 次降为 0，QPS 提升 12.5%–16.6%，P95 下降 15.6%–20.7%，P99 下降 25.6%–34.0%**；高并发下长尾改善更明显，说明缓存主要价值是消除数据库连接排队。

不建议写成"性能提升 10 倍"这类无法复现的数字。
