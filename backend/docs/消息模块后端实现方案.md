# 消息通知模块 · 后端实现方案

> 面向"旅游信息管理平台"后端（Spring Boot，Base URL `http://localhost:8081/travel/`）。
> 前端读取链路已全部完成：消息中心页（`src/views/message/MessageCenter.vue`）、用户端/后台顶栏铃铛未读徽标（`src/layouts/UserLayout.vue`、`src/layouts/MainLayout.vue`）、接口封装（`src/api/message.js`）。
> 当前缺口：**后端没有任何业务节点往 message 表写数据**，且以下接口中 `markRead`、`unreadCount` 尚未实现。本文档定义数据模型、表结构、全部 API 与消息产生时机。

## 0. 统一约定（与全站一致）

| 项 | 约定 |
|---|---|
| Base URL | `http://localhost:8081/travel/` |
| 认证 | JWT，`Authorization: Bearer <token>`；除 `unreadCount` 外全部要求登录 |
| 返回体 | `{ code: 1, msg: "ok", content: ... }`，`code !== 1` 视为失败；空结果用 `code: 0, msg: "没有找到数据"` |
| 分页参数 | `page`（从 1 开始）、`size`；返回 `content: { content: [], totalElements, totalPages }` |
| 通用排序参数 | `orderCol` + `orderDirect`（`ASC`/`DESC`，已在 collect 模块实现）；消息模块**默认按 `id DESC`**（最新消息在前） |
| 删除 | 逻辑删除 |
| 时间字段 | `createTime`，JSON 输出格式 `yyyy-MM-dd'T'HH:mm:ss`（与其他模块一致，前端 `formatTime` 已兼容） |

## 1. 数据模型

### 1.1 字段定义（实体 Message）

> 最终约定（全模块统一）：接收人一律用 `userId` 表达——实体里 `userId` 为关联用户对象；**对外接口层全部用 `userId` 传用户ID 数字**（queryByPage 查询参数、unreadCount 参数、add 的 body）。注意 queryByPage 不能用实体直接绑定 GET 参数（userId 是对象类型会 400），需单独 `@RequestParam Long userId` 或查询 DTO 接收。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | Long | 主键自增 | 消息ID |
| `userId` | TravelUserEntity | 非空 | 接收人（关联用户对象；JSON 输出用户摘要，password 已用 `@JsonProperty(WRITE_ONLY)` 屏蔽） |
| `type` | Integer | 非空，默认 0 | 消息类型：**0=系统公告、1=订单、2=审核** |
| `title` | String(100) | 非空 | 消息标题（列表页加粗展示） |
| `content` | String(500) | 非空 | 消息正文 |
| `isRead` | Integer | 非空，默认 0 | **0=未读、1=已读**（注意不是布尔） |
| `deleted` | Integer | 非空，默认 0 | 逻辑删除：0=正常、1=已删除 |
| `createTime` | DateTime | 非空，默认当前时间 | 创建时间 |
| `updateTime` | DateTime | 可空 | 更新时间（标记已读时刷新） |

> ⚠️ 前端强依赖的输出字段名：`userId`、`type`、`title`、`content`、`isRead`、`createTime`、`id`。

### 1.2 建表 SQL（MySQL）

```sql
CREATE TABLE `message` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '消息ID',
  `user_id` BIGINT       NOT NULL COMMENT '接收人用户ID',
  `type`        TINYINT      NOT NULL DEFAULT 0 COMMENT '类型：0系统 1订单 2审核',
  `title`       VARCHAR(100) NOT NULL COMMENT '标题',
  `content`     VARCHAR(500) NOT NULL COMMENT '正文',
  `is_read`     TINYINT      NOT NULL DEFAULT 0 COMMENT '0未读 1已读',
  `deleted`     TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除：0正常 1已删除',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` DATETIME     NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_receiver_read` (`receiver_id`, `is_read`, `deleted`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户消息表';
```

> 列名若需与库内其他表风格统一（如全驼峰列名），改列名即可，实体映射对上就行。`idx_receiver_read` 覆盖未读数统计的高频查询。

## 2. API 定义（前端已按此调用，勿改路径）

### 2.1 分页查询消息 `GET message/queryByPage`

| 参数 | 必填 | 说明 |
|---|---|---|
| `userId` | ✅ | 接收人用户ID（前端始终传当前登录用户）。⚠️ 必须用 `@RequestParam Long userId` 或查询 DTO 单独接收，**不能用 MessageEntity 绑定**（userId 是对象类型，GET 字符串会 400） |
| `type` | ✗ | 类型过滤：0/1/2 |
| `isRead` | ✗ | 已读过滤：0/1 |
| `page` / `size` | ✅ | 分页，page 从 1 开始 |
| `orderCol` / `orderDirect` | ✗ | 可选；默认 `id DESC` |

返回示例：

```json
{
  "code": 1,
  "msg": "找到数据！",
  "content": {
    "content": [
      {
        "id": 5,
        "userId": { "id": 1, "nickname": "张三", "avatar": "..." },
        "type": 2,
        "title": "审核通知",
        "content": "你发布的攻略《北京故宫避坑指南》已通过审核",
        "isRead": 0,
        "createTime": "2026-09-07T10:30:00"
      }
    ],
    "totalElements": 12,
    "totalPages": 2
  }
}
```

无数据时返回 `code: 0, msg: "没有找到数据"`（前端按空态渲染，不报错）。
SQL 要点：`WHERE deleted = 0`，userId 有值时追加 `AND user_id = #{userId}`，type/isRead 有值才追加条件。

### 2.2 未读数量 `GET message/unreadCount?userId={userId}`

- 返回 `content` 直接是**数字**：`{ "code": 1, "msg": "ok", "content": 3 }`
- SQL：`SELECT COUNT(*) FROM message WHERE receiver_id=? AND is_read=0 AND deleted=0`
- 前端在每次路由切换时调用（顶栏红点），查询轻量，走 `idx_receiver_read` 索引即可

### 2.3 标记已读 `POST message/markRead`

- Body 二选一：`{ "id": 5 }` 单条，或 `{ "ids": [5, 6, 7] }` 批量（前端"全部已读"用批量）
- 处理：`UPDATE message SET is_read = 1 WHERE id IN (...) AND deleted = 0`
- 返回：`{ "code": 1, "msg": "已标记已读" }`
- 要求：**幂等**——重复标记已读的消息也返回成功；只能标记 `receiverId = 当前登录用户` 的消息，操作他人消息返回 `code: 0`

### 2.4 新增消息 `POST message/add`

- Body：`{ "userId": { "id": 1 }, "type": 0, "title": "系统公告", "content": "..." }`——**userId 必须是对象**（实体关联绑定，传数字会 400），`isRead` 固定落 0
- 用途：①管理员群发系统公告（前端 UI 待加，接口先就绪）②也可作为业务触发点的统一落库入口
- 校验：userId 必须是存在的、未删除的用户；type 只允许 0/1/2

### 2.5 详情 / 编辑 / 删除

| 接口 | 方法 | 说明 |
|---|---|---|
| `message/queryById/{id}` | GET | 返回单条消息对象（结构同 2.1 数组元素） |
| `message/edit` | POST | Body 含 `id` + 任意字段（title/content/type/isRead），管理员修正用 |
| `message/deleteById/{id}` | POST | **逻辑删除**（`deleted = 1`）；只能删自己收到的消息（或管理员） |

删除后消息不得出现在 queryByPage 与 unreadCount 统计中。

## 3. 消息产生时机（核心业务逻辑）

消息一律**在业务操作落库的同一事务内**插入 message 表；插入失败建议 catch 后仅记日志、不回滚主业务（消息丢失可容忍，业务失败不可容忍）。

### 3.1 攻略审核完成 → type=2

触发点：`strategy/edit` 中 `auditStatus` 发生 `0 → 1` 或 `0 → 2` 时

```java
// receiverId = 攻略发布者 strategy.userId.id
title   = "攻略审核结果";
content = auditStatus == 1
    ? "你发布的攻略《" + strategy.title + "》已通过审核"
    : "你发布的攻略《" + strategy.title + "》未通过审核，请修改后重新提交";
```

### 3.2 路线审核完成 → type=2

触发点：`route/edit` 中 `status` 发生 `0 → 1` 或 `0 → 2` 时，同上，文案换「路线《name》」。

### 3.3 评论审核完成 → type=2

触发点：`strategyComment/edit` 审核状态变更时，receiverId = 评论者 userId，content 引用评论内容前 20 字。

### 3.4 订单 → type=1

| 时机 | title | content |
|---|---|---|
| `scenicOrders/add` 下单成功 | "下单成功" | 「已为《景点名》生成订单 ORDERxxx，请及时支付」 |
| `scenicOrders/edit` 中 payStatus `0 → 1` | "支付成功" | 「订单 ORDERxxx 已支付，祝您游玩愉快」 |

### 3.5 系统公告 → type=0

由管理员通过 `message/add` 手动发送（管理后台的发送 UI 为后续可选项），receiverId 为目标用户；如需全员广播，循环为每个未删除用户插一条（数据量小可接受）。

## 4. 安全与校验规则

1. `queryByPage` / `unreadCount` / `markRead` / `deleteById` 必须携带 JWT
2. 普通用户只能查询/标记/删除 `receiverId = 自己` 的消息；越权返回 `code: 0`（userRole=1 管理员可管理全部）
3. `type` 只接受 0/1/2；`isRead` 只接受 0/1
4. `markRead` 对已读消息重复调用返回成功（幂等）
5. 逻辑删除的消息：列表不可见、不计入未读数
