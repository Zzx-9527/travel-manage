## 一、完整版（7 条，细节最全，适合项目占大半页版面）

### 旅游管理平台（后端）｜ Java 后端开发｜【个人项目 / 团队项目，本人负责后端】

**项目描述：** 面向景点、路线、攻略、门票订单、收藏与站内消息的旅游业务平台，为管理端和用户端提供独立 RESTful API。独立完成后端从数据库建模、接口开发到性能验证的全过程，共 12 个业务模块、63 个接口。

**技术栈：** Spring Boot 2.7 / MyBatis-Plus 3.5 / MySQL / Redis（Lettuce + Redisson）/ Sa-Token / HikariCP / Knife4j + SpringDoc / Maven

**主要工作与成果：**

- **接口与分层**：按 Controller–Service–Mapper 三层拆分，统一 `ReturnVO` 响应结构与全局异常处理（鉴权异常统一转 401/403）；基于 MyBatis-Plus（`BaseMapper` + `@TableField` 自动填充）配合自定义 XML 完成联表映射、软删除与分页；设计 12 张业务表，独立交付 63 个接口。
- **门票库存与订单事务**：新增景区日容量与票种日库存两张表，下单在同一本地事务内按“容量 → 票种 → 订单”顺序执行条件扣减（`remaining >= n` 且以影响行数判定），不依赖 Redis 或分布式锁防超卖；取消采用“先条件改状态、后条件回补”，重复取消不会二次回补；未支付订单 30 分钟由定时任务按 id 游标分批取消，模拟支付与取消通过带状态条件的更新互斥；库存生成用 `INSERT IGNORE` + 组合唯一键保证每日补齐幂等、不重置已售库存。
- **鉴权体系重构**：用 **Sa-Token + Redis 会话**替换无状态 JWT，实现登出即时失效、30 分钟无操作自动过期、多端独立 token 与管理员踢人下线；通过 `StpInterface` + `@SaCheckRole` 做接口级角色鉴权，并以 `SecurityUtil` 统一从 token 取身份，修复了"前端传 userId 即可越权读写他人订单/收藏/消息"的越权漏洞。
- **缓存设计**：抽象 Cache-Aside 模板统一收口缓存读写，用**空值哨兵**防穿透、**TTL ±10% 随机抖动**防雪崩、**`SETNX` + Lua 原子释放的手写互斥锁 + 双重检查**防击穿；写操作统一"先更库、后删缓存"，Redis 异常时全部降级回源，缓存故障不影响接口可用性。
- **限流与幂等**：登录用 **Lua 固定窗口限流**（`INCR`+`EXPIRE` 原子执行，单 key/IP、60 秒自动过期），下单用 **Redisson `RBucket.trySet`** 做 5 秒防重复提交；排查中发现 `RRateLimiter` 每个 IP 会写 3 个无 TTL 的 key，改为手写实现后 key 数量降为原来的 1/3 且全部自动过期。
- **浏览量异步回写**：详情页高频计数只做 Redis `INCR`，`@Scheduled` 每 60 秒用 **SCAN**（禁用 `KEYS`）批量回写 MySQL，严格"先落库、再 `DECRBY`"，写库失败保留计数下轮重试（at-least-once，宁可多计不可少计）；回写任务用 Redisson 锁互斥，避免多实例重复累加。
- **性能验证**：自研 JDK 单文件压测工具（`HttpURLConnection` + 固定线程池，规避 PowerShell 客户端开销），对景点详情接口做缓存前后对比（50/100/200 并发、1–4 万请求）：**QPS 提升 12.5%–16.6%，P95 下降 15.6%–20.7%，P99 下降 25.6%–34.0%，数据库查询量由每请求 1 次降为 0**。
- **工程治理与安全**：以 Knife4j + SpringDoc 替换已停更的 springfox，移除 log4j 1.x 等死依赖，连接池 dbcp2→HikariCP、打包 war→可执行 jar；文件上传采用 UUID 命名 + 后缀/Content-Type 白名单 + 路径归一化校验，防重名与路径穿越。

## 五、可能被追问的点（自查用）

| 追问 | 要点 |
|---|---|
| 为什么 JWT 换 Sa-Token？ | JWT 签发后不可撤销，登出只是前端删 token；会话存 Redis 后可登出、踢人、续期、查在线列表，代价是每次鉴权多一次 Redis 查询 |
| 手写锁为什么不用 Redisson？ | 缓存重建是单 key、短临界区、幂等操作，`SETNX`+UUID+Lua 约 15 行；Redisson 留给需要可重入、等待队列、看门狗的场景 |
| 锁怎么保证不误删别人的？ | 锁值为 UUID，释放时用 Lua 做"比对 + 删除"原子操作，TTL 兜底防死锁 |
| 缓存一致性怎么保证？ | Cache-Aside，先更库后删缓存，删除失败靠 TTL 兜底，接受最终一致 |
| Redis 挂了会怎样？ | 缓存降级回源、锁降级放行、限流放行；鉴权不可降级（返回 401），否则等于可以猜身份 |
| 为什么浏览量先落库再扣 Redis？ | 顺序反了一旦写库失败或进程崩溃，这部分浏览就永久丢失；现在的顺序最坏是多计一次，可接受 |
| 库存怎么防超卖？ | 不做“先查余量再扣减”：直接用 `UPDATE ... SET remaining=remaining-n WHERE remaining>=n`，以影响行数判断，配合本地事务；容量与票种固定先容量后票种，降低死锁概率 |
| 取消会不会重复回补？ | 先执行带 `status=0` 条件的更新，只有真正把状态改成已取消的那一次才回补；历史订单 `stock_reserved=0`，不参与回补 |
| 为什么不用 Redis 预扣库存？ | 本期单库、低并发规模，MySQL 条件更新已能保证不超卖；Redis 预扣会引入缓存与库的最终一致、回补补偿和宕机恢复问题，收益不足以抵消复杂度 |
| 模拟支付和超时取消会打架吗？ | 两者都是 `WHERE status=0` 的条件更新，数据库行锁保证只有一个成功；支付多一个“创建未满 30 分钟”条件 |

## 六、MyBatis-Plus 实际使用边界（别写超了）

**用到的**：`mybatis-plus-boot-starter` 依赖；Mapper 全部 `extends BaseMapper<T>`；实体用 `@TableField(fill = ...)` 标公共字段、`@TableField(exist = false)` 排除关联对象；实现 `MetaObjectHandler` 提供自动填充扩展点。

**没用到的**：分页插件（`PaginationInnerInterceptor` / `IPage`，实际是手写 `count` + `limit` + `PageImpl`）、`QueryWrapper` / `LambdaQueryWrapper`（实际是 XML `<if>` 动态 SQL）、`IService` / `ServiceImpl`、`@TableName` / `@TableId` / `@TableLogic`（表名、主键、软删除都手写在 XML）。

**已知坑**：Mapper 接口重新声明了 `insert` / `update` / `deleteById`，XML 有同名语句，实际执行手写 SQL、MP 内置方法被覆盖，所以自动填充不触发，Service 层手动补 `createTime` / `updateTime`。

**安全写法**：`基于 MyBatis-Plus（BaseMapper + @TableField 自动填充）配合自定义 XML 完成联表查询、软删除与分页`。
**危险写法**：`使用 MyBatis-Plus 分页插件 / 条件构造器 / Lambda 查询`——一追问就露。
